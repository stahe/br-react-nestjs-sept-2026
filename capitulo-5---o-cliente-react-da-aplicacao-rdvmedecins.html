    6. Capítulo 5 - O cliente [React] da aplicação [RdvMedecins]

    Este capítulo detalha, arquivo por arquivo, o conteúdo da pasta [rdvmedecins-react-client] incluída neste documento, usando o formato adotado ao longo de todo o curso: código-fonte numerado linha a linha, seguido de uma seção “Vamos comentar este código:”. Cada pasta do projeto também contém o seu próprio [README.md].

    6.1. Visão geral da arquitetura

    Como no documento original, o cliente segue uma arquitetura em camadas, que chamaremos aqui de V-Services (View-Services):

    Vale notar uma diferença de terminologia: no AngularJS 1.x, a View (o template HTML) e o Controller (a classe JavaScript associada) eram duas entidades separadas, ligadas por $scope. No [React], elas são combinadas em uma única entidade, o componente (veja o capítulo anterior) — exatamente como no [Angular], embora a forma seja diferente (uma função em vez de uma classe) — e é por isso que, daqui em diante, falaremos simplesmente em “componentes” onde o documento original distinguia entre view e controller.

    Como no documento original, os componentes NUNCA se comunicam diretamente com o servidor: esse papel é reservado exclusivamente à camada de Serviços (aqui, o hook useAppointmentService() e o contexto AuthContext). Este é um princípio de projeto que se aplica igualmente ao AngularJS 1.x e também ao [Angular] e ao [React] — ele não mudou.

    6.2. Árvore do projeto

    Esta divisão segue diretamente o fluxo do documento original (login, seleção de médico/dia, exibição da agenda, reserva), apenas organizada aqui em componentes funcionais [React] em vez de controllers/views separados do AngularJS 1.x, ou de componentes standalone do [Angular]. Há duas diferenças estruturais em relação à estrutura de diretórios do [Angular] deste curso:

    • o componente raiz é composto por três arquivos (App.tsx, App.css, README.md) em vez de cinco (app.ts, app.html, app.css, app.config.ts, app.routes.ts): [JSX] mescla a classe e o template, e o [React] não tem um arquivo de configuração da aplicação equivalente a app.config.ts (veja “Configuração da aplicação” abaixo);
    • Aparece uma pasta `core/context/` , ausente da variante [Angular]: ela contém os hooks personalizados e os arquivos de [React] [Context] que fazem as vezes dos serviços injetáveis ([SettingsService], [AuthService], [LanguageService]) da variante [Angular] — esse mecanismo (hooks + [Context]) foi apresentado no capítulo anterior, junto com um exemplo genérico (veja o capítulo anterior, “Compartilhando lógica”).

    O [Bootstrap] 5 é usado em todas as views (importado em main.tsx; veja abaixo) — uma evolução direta do Bootstrap 3, já usado pelo documento original, e idêntico ao da variante [Angular] deste curso.

    Ao contrário do servidor [NestJS] (módulo [commonjs], veja o Capítulo 3), este projeto roda em módulos ECMAScript nativos (import/export) — exatamente como a variante [Angular] deste curso (“module”: “preserve” em tsconfig.json, veja abaixo).

    Enquanto a variante [Angular] deste curso separa [tsconfig.json] (base comum) e [tsconfig.app.json] (por meio do mecanismo de project references), este projeto [React] menor consiste em um único arquivo — já que as verificações de tipos dos templates ([Angular] e strictTemplates) não têm equivalente aqui de qualquer modo: é o próprio compilador TypeScript que verifica o [JSX], como qualquer outro arquivo .tsx.

    Vamos comentar este código:

    • linha 6: .use(HttpBackend) — carrega cada dicionário por meio de uma requisição HTTP GET, na URL formada por [backend.loadPath] (linha 15): [/i18n/fr.json] ou [/i18n/en.json], EXATAMENTE a mesma URL construída por [TranslateHttpLoader] no lado [Angular] (prefix: '/i18n/', suffix: '.json'), de modo que [public/i18n/fr.json] e [public/i18n/en.json] (veja abaixo) possam ser reutilizados como estão, sem nenhuma modificação;
    • linha 7: .use(initReactI18next) — conecta o [i18next] ao [React]: fornece o hook useTranslation() usado em todo componente de features/, e o hook [Context] do React (interno à biblioteca, não visível aqui), que dispara uma nova renderização completa de toda a interface quando o idioma muda — o equivalente do que, no lado [Angular], o decorador [TranslatePipe] combinado com [provideTranslateService(...)] faz;
    • linha 9: lng: navigator.language?.toLowerCase().startsWith('fr') ? 'fr' : 'en', — idioma inicial (francês se o navegador estiver configurado em francês, inglês caso contrário; fallbackLng: 'en' na linha 10); o hook [useLanguage()] (veja core/context/language.context.tsx abaixo) o substitui imediatamente pela seleção armazenada em localStorage, se houver — exatamente como lang: 'en' em [app.config.ts] no lado [Angular];
    • linhas 11–13: interpolation: { escapeValue: false, }, — o [React] já faz o escape de HTML por conta própria (proteção contra vulnerabilidades XSS): não há necessidade de o [i18next] fazer isso uma segunda vez.

    No documento original (2014), o cliente AngularJS 1.x usava a biblioteca angular-translate para essa mesma necessidade — a predecessora, dentro do ecossistema AngularJS 1.x, de [@ngx-translate/core] (a variante [Angular] deste curso) e, aqui, de [i18next]. As DUAS bibliotecas modernas ([ngx-translate] no lado [Angular], [i18next] no lado [React]) carregam dicionários JSON por meio de uma simples requisição HTTP GET, usando o mesmo esquema “um arquivo por idioma, uma seção por tela”.

    api.getDoctorScheduleOfDay(lastDoctorId.current, lastDay.current).then(setSchedule)
      .catch((err: unknown) => setError(String((err as Error).message ?? err)));
  }

  return (
    <div className="container py-4">
      <nav className="navbar navbar-expand-sm navbar-dark bg-primary rounded mb-4 px-3">
        <span className="navbar-brand mb-0">{t('APP.TITLE')}</span>
        <div className="d-flex align-items-center gap-2">
          <div className="btn-group btn-group-sm" role="group" aria-label="FR / EN">
            <button type="button" onClick={() => language.changeLanguage('fr')}
              className={'btn ' + (language.currentLanguage === 'fr' ? 'btn-light' : 'btn-outline-light')}>FR</button>
            <button type="button" onClick={() => language.changeLanguage('en')}
              className={'btn ' + (language.currentLanguage === 'en' ? 'btn-light' : 'btn-outline-light')}>EN</button>
          </div>
          {auth.isLoggedIn && (
            <>
              <span className="badge text-bg-light text-primary">{auth.role}</span>
              <span className="text-white">{auth.name}</span>
              <button type="button" className="btn btn-sm btn-outline-light" onClick={onLogout}>
                {t('APP.LOGOUT')}
              </button>
            </>
          )}
        </div>
      </nav>

      <div className="row g-2 align-items-center mb-4">
        <div className="col-auto">
          <label className="form-label mb-0" htmlFor="input-server-url">{t('APP.SERVER_URL_LABEL')}</label>
        </div>
        <div className="col-sm-4">
          <input id="input-server-url" type="text" className="form-control form-control-sm"
            defaultValue={settings.apiBaseUrl} onChange={(e) => settings.setApiBaseUrl(e.target.value)} />
        </div>
      </div>

      {error && <div className="alert alert-danger" role="alert">{error}</div>}

      {!auth.isLoggedIn ? (
        <Login />
      ) : (
        <>
          <DoctorDayPicker doctors={doctors} onSearch={onSearchSchedule} />
          <Schedule schedule={schedule} canEdit={auth.isAdmin}
            onBook={onBookingRequest} onCancel={onCancelAppointment} />
          <BookingDialog open={slotBeingBooked !== null} slot={slotBeingBooked}
            clients={clients} onConfirm={onConfirmBooking} onClose={() => setSlotBeingBooked(null)} />
        </>
      )}
    </div>
  );
}

    Vamos comentar este código:

    • linhas 27–28: const lastDoctorId = useRef<number | null>(null); const lastDay = useRef<string | null>(null); — armazenamos a última busca (médico + dia) para poder atualizar a agenda após uma reserva ou um cancelamento. Um [useRef](), e não um [useState](): esses dois valores nunca são usados diretamente para exibição (ao contrário de “schedule” ou “error”), portanto não há necessidade de redesenhar o componente quando mudam — exatamente o mesmo raciocínio que, no lado do [Angular], manteve [lastDoctorId/lastDay] como simples campos privados em vez de signals; modificar um [useRef]() (.current = …) não redesenha o componente, ao contrário de um [setXxx()] de [useState]();
    • linhas 30–35: useEffect(() => { if (auth.isLoggedIn) { loadInitialLists(); } }, [auth.isLoggedIn]); — reexecuta seu corpo toda vez que [auth.isLoggedIn] muda — o equivalente direto de [effect(() => { if (this.auth.isLoggedIn()) { … } })] no lado do [Angular]. Ele também é executado uma vez quando o componente é montado: se uma sessão já estava armazenada em [localStorage] (recarregamento da página), as listas são carregadas imediatamente na inicialização, sem esperar por um login;
    • linhas 89–94: <div className="btn-group btn-group-sm" …> …FR…EN… </div> — o seletor de idioma fica visível (inclusive na tela de login); o selo do papel, o nome e o botão de logout, porém, só são exibidos se [auth.isLoggedIn] (linhas 95–103, [{auth.isLoggedIn && (…)})] — exatamente a mesma lógica dos lados [Angular] and [(@if (auth.isLoggedIn()) { … })] ;
    • linhas 119–130: {!auth.isLoggedIn ? ( <Login /> ): ( <>…</> )} — enquanto [useAuth().isLoggedIn] for igual a false, este componente exibe apenas <Login />; como todas as rotas do servidor agora são protegidas por [JwtAuthGuard] (Capítulo 3), seria inútil (e causaria erros 401) carregar médicos/clientes/agenda antes do login — exatamente o mesmo raciocínio do [Angular];
    • linhas 123–127: <DoctorDayPicker doctors={doctors} onSearch={onSearchSchedule} /> … — os três componentes de “lógica de negócio” de features/ são montados aqui, cada um recebendo suas props (dados + funções de callback) — o equivalente exato do template [app.html] no lado do [Angular], onde os mesmos três componentes apareciam com [doctors]="doctors()" ([search)="onSearchSchedule($event)"]….

    Estado ([useState/useRef]), efeito ([useEffect]) e manipuladores de eventos (as funções onXxx): são exatamente os quatro componentes já apresentados no capítulo anterior, aplicados aqui ao componente raiz inteiro — nada de novo foi introduzido neste arquivo; ele foi simplesmente montado.

    6.13. O que fica fora do escopo ou adiado

    O modo “debug” (exibição do template bruto da view atual) do cliente AngularJS 1.x original é um recurso deliberadamente omitido deste port, assim como na variante [Angular] deste curso — ele não aparecerá em uma etapa posterior do curso (veja o Capítulo 6, Conclusão, para a justificativa dessa decisão). A configuração de um atraso artificial de rede, porém, de fato fica adiada para uma etapa posterior nas duas variantes.

    Duas diferenças adicionais, específicas deste port em [React], merecem ser mencionadas aqui:

    • os testes unitários (ausentes tanto deste projeto quanto do projeto [Angular] deste curso) seguiriam uma abordagem diferente no [React]: em vez do TestBed (específico do [Angular]), o ecossistema [React] normalmente recorre ao [React Testing Library] — não apresentado neste documento;
    • a verificação de tipos dos templates ([Angular] strictTemplates, veja o capítulo anterior) não tem equivalente que precise ser configurado separadamente no lado do [React]: é o próprio compilador TypeScript que verifica o [JSX], como qualquer outro arquivo .tsx — uma simplificação da configuração, ao custo, em teoria, de uma integração ligeiramente menos profunda entre a linguagem de template e o sistema de tipos (na prática, neste projeto, nenhuma diferença observável).
